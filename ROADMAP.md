# ROADMAP

This repo is currently a lightweight backup/export of Toggl Track time entries:
- Raw exports live in `2023.csv`, `2024.csv`, `2025.csv` (note: export format differs slightly between years).
- Weekly visualizations are pre-rendered PNGs in `2023/`, `2024/`, `2025/`, generated by `plot.py`.

The goals below evolve this into an automated pipeline + a browsable/searchable GitHub Pages “diary”, with editing performed in the frontend instead of inside Toggl.

## Guiding Decisions (Need Alignment Early)

1. **Privacy / audience**
   - Repo is **private**; GitHub Pages is expected to stay private as well (no public publishing).
   - Whether descriptions (diary text) should ever be shipped to the browser unencrypted.
2. **Source of truth**
   - **Phase 0–1:** Toggl remains the system of record; repo mirrors it.
   - **One-way sync only:** no edits are pushed back to Toggl.
3. **Data format**
   - Keep raw Toggl snapshots for auditability.
   - Maintain a normalized, stable schema for the website/search/editor to consume.
4. **Time zones & day boundaries**
   - Canonical timezone for grouping: **CET** (implemented as `Europe/Berlin` to handle DST).
   - Define behavior for entries spanning midnight.

## Target Architecture (High Level)

- **Ingest (GitHub Actions cron)**: pull from Toggl API → store as `data/raw/toggl/*.json`.
- **Normalize**: transform raw → `data/entries/{year}.json` (or chunked by month) + derived indices.
- **Publish (GitHub Pages)**: static site reads normalized JSON + precomputed search index.
- **Edit (Frontend)**: user edits entries in the site; changes are saved as repo commits (via GitHub API) and/or queued as “overrides” applied during normalization.

## Milestones

### M0 — Repository Layout & Schema

- Add a `data/` directory with:
  - `data/raw/toggl/` (verbatim-ish API payloads, partitioned by date pull)
  - `data/entries/` (normalized canonical entries used by the site)
  - `data/index/` (search index + lightweight metadata for fast browsing)
- Define a canonical entry schema (example fields):
  - `id` (Toggl time entry id; stable key)
  - `start`, `end` (ISO-8601 with timezone offset)
  - `duration_seconds`
  - `description`, `project`, `client`, `tags`, `billable`
  - `source` (`toggl` | `manual`)
  - `updated_at` (for merge/conflict handling)
- Create a small validation script to fail CI when schema breaks.

### M1 — (0) Automated Toggl Sync via GitHub Actions

- Implement `scripts/toggl_sync.py` (or a small Node script) that:
  - Reads secrets (`TOGGL_API_TOKEN`, `TOGGL_WORKSPACE_ID`, optional project map).
  - Fetches time entries incrementally (plus a “lookback window” to catch edits).
  - Writes raw pulls to `data/raw/toggl/…`.
  - Updates normalized `data/entries/…` deterministically.
  - Avoids duplicate entries; handles edits/deletes (decision needed: keep tombstones?).
- Add `.github/workflows/toggl-sync.yml`:
  - `schedule:` cron (e.g., hourly or daily)
  - `workflow_dispatch:` for manual runs
  - Commits changes back to `main` with a clear message (e.g., `sync: toggl`).
- Add a “dry run” mode for debugging in PRs without writing.

### M2 — (1) GitHub Pages: Browse + Search

- Choose deployment model:
  - **Simple**: serve from `docs/` (no build step), site loads `data/…` directly.
  - **Better**: build to `dist/` and deploy via `actions/deploy-pages` (recommended).
- Create `site/` (or `web/`) static app:
  - Timeline views: day / week / month; project/tag filters.
  - Full-text search over descriptions (precomputed index via `flexsearch`/`lunr`).
  - Deep links: `/#/date/2025-05-20`, `/#/entry/<id>`, `/#/search?q=…`.
  - Optional: show existing `YYYY/<week>.png` plots as a “weekly overview” tab.
- Add build step that produces:
  - `data/index/search.json` (or chunked indices)
  - `data/index/summary.json` (counts, totals per project/tag/day)

### M3 — (2) Frontend Editor (Replace Toggl-Based Editing)

- Decide on edit persistence strategy:
  1. **Repo-only overrides (safe, one-way from Toggl)**:
     - Store edits in `data/overrides/{id}.json` (or a single `overrides.json`).
     - Normalizer overlays overrides on top of raw Toggl entries.
  2. **Two-way sync (advanced)**:
     - Frontend edits commit to repo + Action pushes updates back to Toggl via API.
     - Requires conflict resolution rules and careful audit logs.
- Implement editor UX:
  - Edit `description`, `project`, `tags`, `billable`, start/stop times.
  - Validation (no negative durations, ISO timestamps, overlaps flagged optionally).
  - “Draft” state stored locally until saved.
- Implement saving mechanism:
  - For a static site, easiest is a fine-grained GitHub PAT entered by the user and used only to write commits via GitHub REST API.
  - Alternative: export a patch/JSON and apply via local script (no browser token).
- Add an “edit log” (append-only) to make changes auditable/reversible.

### M4 — Quality, Safety, and Backups

- Add CI checks: schema validation, lint/format for scripts, basic unit tests for normalization.
- Add a “redaction” mode for publishing a public site (strip sensitive fields).
- Add export utilities (CSV/JSON) and periodic snapshot tagging.
- Document setup in a `README.md` (secrets, running locally, deploying pages).

## Open Questions (To Answer Before Heavy Implementation)

- How should the site handle privacy in-browser (e.g., optional local-only encryption for descriptions)?
- How should entries spanning midnight be grouped (split vs single entry shown on start day)?
- Confirm replacing `plot.py` PNG workflow with an interactive web visualization (no new PNG generation).
